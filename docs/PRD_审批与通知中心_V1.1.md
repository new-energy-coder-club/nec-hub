## 1. 背景与问题

对标文章的"邮件OA审批"由三个互相独立的部件组成，缺一不可：

| 对标部件 | 说明 | 我方现状 |
|---|---|---|
| 审批中心 | 中台侧栏"审批"入口，聚合待办（角标数量） | 代码 0；V2.0 FE-09（P2）仅一句"聚合飞书审批待办" |
| 标杆审批应用 | 申请 → 审批人收到通知 → 处理 → 状态回写 | 代码 0；V2.0 FE-08（P1）仅有用户故事 |
| 邮件通道 | 生成确认邮件草稿、自动抄送 | 代码 0；Worker 无法直发 SMTP，通道未选型 |

**本期业务范围（V1.1 更新）**：四条审批流程共用一套引擎与通道——

| 流程 | type 标识 | 申请人 | 核心审批人 | 一句话价值 |
|---|---|---|---|---|
| 报销审批 | `reimburse` | 全队 | 财务/队长 | 交发票 → 审批 → 打款，状态自动回写 |
| 机械图纸审批 | `drawing` | 机械组 | 机械组组长 | 图纸不过审不进加工，版本留痕 |
| 硬件采购/领用审批 | `hardware` | 全队 | 组长 → 队长/指导（金额阈值） | 买东西/领库存有审批，台账自动增减 |
| 合规审批 | `compliance` | 运营/宣传为主 | 运营组组长 → 指导老师 | 对外发布/合作/授权先审后发，可追溯 |

**为什么现在写详细 PRD**：FE-01 登录态已上线生产（2026-10-12 部署），审批链路的公共前置只剩 FE-02（底表落地）。V2.0 的 FE-08/FE-09 粒度只到"用户故事 + 3 条验收"，无法直接开发——缺审批引擎选型、状态机、字段级表结构、接口契约、通知通道选型。本 PRD 补齐这些。

## 2. 目标与成功指标

**产品目标**：任何一条审批线的用户，从提交到结果通知全程零人工传话；审批结果自动回写对应底表；全队按角色看到正确的待办与汇总。

| 指标 | 定义 | 目标值 | 测量方式 |
|---|---|---|---|
| 审批线上化率 | 走审批中心的单数 / 四类业务总单数 | 上线 4 周后 ≥ 80% | 各底表"来源"字段统计 |
| 审批时延 | 提交 → 审批人收到飞书通知 | P95 ≤ 2 分钟 | 审批实例时间戳差 |
| 状态回写准确率 | 审批结果与底表状态一致的单数占比 | ≥ 98%，不一致需人工可解释 | 对账抽查 |
| 通知到达率 | 通知发送成功 / 应发通知 | ≥ 95%（失败自动降级通道） | 通知发送日志 |
| 待办准确性 | 待办条显示数与飞书审批中心实际待办数一致 | 100%（≤5 分钟缓存窗口） | 验收测试用例 |
| 新增流程成本 | 从提出到上线第 5 条流程所需开发量 | 零代码（仅配置） | 架构走查 |

## 4. 总体设计

### 4.1 三个子系统

```
┌──────────────────────────────────────────────────────────────┐
│ 门户层                                                        │
│  · 各流程申请页（/apps/reimburse/、/apps/drawing/ 等，           │
│    均经 deploy_app 上架，流程间只换表单 schema 与 type）          │
│  · 待办条（首页顶部，所有 Tab 可见，按 type 分图标）               │
├──────────────────────────────────────────────────────────────┤
│ 中台 Worker 新增模块（引擎 flow-agnostic，不为单流程硬编码）       │
│  · /api/approvals        审批封装：发起(type 参数化)/事件回调/轮询   │
│  · /api/todos            待办聚合（飞书审批 + 逾期任务）           │
│  · flows 配置            KV `flows:config`：type → 底表/审批定义/  │
│                          字段校验规则/审批路由阈值                  │
│  · notify 模块           通知服务（飞书机器人 webhook 主通道）      │
│  · mailer 模块           邮件通道（Resend HTTP API，降级通道）      │
│  · MCP 新增工具：submit_approval / list_todos / send_notice      │
├──────────────────────────────────────────────────────────────┤
│ 飞书侧                                                        │
│  · 飞书审批（引擎）：4 个审批定义，状态变更事件订阅                 │
│  · 群机器人 webhook（通知主通道，可按流程分流）                    │
│  · 多维表格：4 张流程底表（§6.1）+ 队员名单/任务/物资/财务既有表     │
└──────────────────────────────────────────────────────────────┘
```

### 4.2 关键决策

**D1 审批引擎用飞书审批，不自建状态机；引擎必须流程无关（flow-agnostic）。**
理由：① 通知原生（审批机器人自动推送给审批人，免做触达）；② 权限复用飞书（FE-01 原则）；③ 待办可直接拉飞书审批 API；④ 免费版可用（**排期前先用 1 个测试审批验证，验证不过则启动 Plan B**）。
实现要求：`/api/approvals` 的 `type` 参数在 `flows:config`（KV）中查找：approval_code、目标底表 table_id、字段校验规则（声明式 JSON）、金额阈值路由。新增第 5 条流程 = 加一个审批定义 + 建一张底表 + 改一份 KV 配置，**零代码**。
Plan B（降级）：状态机落在各底表"状态"字段，通知走群机器人 webhook，待办条改为查表。语义与接口契约不变，仅引擎实现替换。

**D2 通知主通道 = 飞书群机器人 webhook，邮件 = 降级/可选增强。**
对标文章的"生成邮件草稿抄送 COO"在我们环境落不了地（无 Gmail/企业邮箱 API，Worker 不能 SMTP）。替换为：审批动作实时推飞书群（含审批卡片链接），邮件仅在配置了 `RESEND_API_KEY` 时启用。学生团队场景飞书打开率远高于邮箱，这是对标杆的合理本地化。

**D3 数据不下沉**：审批单明细存飞书（审批实例 + 底表），中台只存映射与短期缓存（KV），退队即失效。

**D4 多群分流（V1.1 新增）**：4 条流程各配一个通知群（报销→财务群、图纸→机械群、硬件→电控群、合规→运营群），未配置时全部 fallback 到主通知群。群机器人 webhook 均为 secret，按 `FEISHU_BOT_WEBHOOK_<TYPE>` 命名。

## 5. 功能需求

优先级：P0 阻塞链路，P1 完整闭环，P2 增强。

### N-01 通知服务（飞书群机器人 webhook）【P0】

**用户故事**：作为系统，任何审批事件都能在 2 分钟内推送到对应流程的飞书群，且失败可感知。

**详细需求**：
- 封装 `notify(env, { flow, title, content, link? })`：按 `flow` 选 webhook（`FEISHU_BOT_WEBHOOK_<TYPE>`），未配置 fallback `FEISHU_BOT_WEBHOOK`。
- 签名实现：若 webhook 含 secret，按飞书加签算法（timestamp + "\n" + secret 的 HMAC-SHA256 → Base64）发送。
- 重试：失败（网络错误/非 0 code）重试 2 次，指数退避（1s/4s）；仍失败写入 KV `notify:failed`（保留 7 天），管理端可查。
- 消息格式：`post` 富文本，标题 + 关键字段表 + "去处理"链接（跳审批详情）。
- 同一事件多群（如报销通过 → 通知申请人所在群 + 财务群）由调用方多次调用 notify，服务本身只保证单次送达。

**验收**：
1. 4 个流程各触发 1 条测试事件，对应群 10 秒内收到格式正确的消息。
2. 故意填错 webhook，重试 2 次后 `notify:failed` 出现记录，接口返回降级提示。

### N-02 邮件通道（Resend）【P2】

**详细需求**：
- 仅当配置 `RESEND_API_KEY` 与 `MAIL_FROM` 时启用；未配置时所有邮件调用返回"通道未启用"，业务不受影响。
- 经 Resend HTTP API 发送（Worker 内 fetch，无 SMTP）。
- 模板：纯 HTML 内联样式一封（审批结果通知），字段：申请人/类型/金额或图纸号/审批链接。
- 免费额度约 100 封/天（以官网为准），只发"审批结果"与"周报摘要"两类低频邮件，其余全走飞书。

**验收**：配置后触发审批通过事件，收件箱收到渲染正确的邮件；未配置时接口明确返回 disabled 而非报错。

### A-01 待办条（V2.0 FE-09 详细化）【P1】

**用户故事**：作为任何角色的审批人，打开中台首页就看到"待我审批的：报销 2 · 图纸 1 · 硬件 0 · 合规 1"，点开即处理。

**详细需求**：
- 位置：门户 Hero 下方横条，未登录不渲染。
- 数据源与缓存：
  - 飞书审批待办：`GET /open-apis/approval/v4/todo`（需 user_access_token——前端场景用当前登录 session 换；见 §7 权限备注），KV `todo:<open_id>` 缓存 5 分钟。
  - 逾期任务：查任务进度表（复用现有 `fetchTableCached`），截止 < 今天 且状态未完成，按负责人过滤当前用户，缓存 5 分钟。
- 展示：按流程 type 分图标与计数，合计角标；点击展开下拉（流程类型徽标 + 标题 + 截止时间 + 跳转链接）。
- 合规流程特殊规则：计划发布时间 T-1 仍在审批中的单，在待办条对**审批人**标红"临期"。
- 角标数字与下拉列表必须一致（同源数据）。

**验收**：
1. 每个流程各造 1 条待审批，登录后 10 秒内条上出现，按 type 计数正确。
2. 点审批项跳飞书处理完返回，≤5 分钟后数字减少（缓存窗口内允许延迟，文档注明）。
3. 无待办时整条隐藏；合规临期标红规则用例通过。

### A-02 审批引擎：发起与状态回写【P0】

**用户故事**：我在任意流程提交后，系统自动发起飞书审批；审批人在飞书点通过后，对应底表状态自动变更，无需任何人手改表。

**详细需求**：
- 发起：`POST /api/approvals`，body 带 `type`。引擎查 `flows:config` 得到 approval_code 与字段校验规则 → 校验（§5 各流程的必填/条件必填）→ 调飞书审批 `POST /approval/v4/instances`（form 按 type 的字段 schema 组装）→ 返回实例 code → 写入对应底表新行（状态="审批中"）。
- 金额阈值路由（引擎通用能力，阈值存 flows:config）：按请求字段（金额/加工费）决定单级/两级/加指导会签，见各流程节。
- 回写（双通道，都做）：
  1. 事件回调：飞书审批状态变更推送到 Worker `POST /api/approvals/events`（配置 encrypt key / verification token），解密验签后按 `approval:map:<实例code>` 找到目标底表行更新状态。
  2. 轮询兜底：Cron Trigger 每 5 分钟扫 4 张底表中"审批中"且 30 分钟未更新的行，逐条 `GET /approval/v4/instances/:code` 同步状态。
- 状态映射：基础映射 `approved→已通过 / rejected→已驳回 / canceled→已撤销`；各流程的后续人工状态（已打款/加工中/已领用/已发布…）由各应用页提供动作按钮驱动（见各流程节）。
- 通知钩子（引擎统一触发）：发起成功 → 流程群"新申请"；通过/驳回 → 通知申请人 + 流程群摘要。

**验收**：
1. 4 条流程各走通一单端到端：提交 → 审批人飞书收到 → 通过 → ≤5 分钟内底表状态正确（两个回写通道各自断一个都能收敛）。
2. 驳回路径每条流程各验 1 次。
3. 校友账号调 `POST /api/approvals` 返回 401；非对应组的队员提交越组流程返回 403（如非机械组提交流程）。
4. 金额阈值边界用例（199/200/500/1000 元）路由正确。

### R-01 报销助手（标杆应用，V2.0 FE-08 详细化）【P1】

**用户故事**：作为队员，我拍一张发票传上去，填金额和事项，系统告诉我材料齐不齐，确认提交后等审批结果就行。

**验收**（沿用并细化 V2.0 FE-08）：

### F-01 机械图纸审批【P1】

**用户故事**：作为机械组队员，我画完加工图提交审批，组长通过后拿图去加工，驳回则按意见改版本重提，全程版本留痕。

**字段与校验**（详见 §6.1 机械图纸表）：图纸名称/图号/版本/所属机构/材料与工艺/加工方式必填；**外协加工时预估加工费必填**；图纸文件 ≥1 个；加急需填原因。

**审批路由**：机械组组长单级；**预估加工费 ≥ 500 元 → 组长→队长顺序会签**。

**流程特有规则**：
- 图号规则 `MECH-<赛季>-<序号>`（申请时由应用页自动生成预览，底表写入时确认唯一）。
- 版本规则：驳回后修改重提 = 新一行记录（图号相同、版本 +0.1，旧行保留只读）——**不允许覆盖旧版本文件**。
- 通过后动作：申请人点"开始加工" → 状态"加工中"；加工完成点"归档" → "已归档"（归档时强建议回传实物照片 1 张，可选）。
- 驳回必须填审批意见，意见随通知推给申请人。

**验收**：
1. 自加工单（单级）与外协单（≥500 两级）各走通一单。
2. 驳回 → V1.1 重提：旧版本行未被覆盖，两行间可互相跳转。
3. 非机械组队员提交返回 403。

### F-02 硬件采购/领用审批【P1】

**用户故事**：作为队员，我申请采购电机或领用库存，组长审必要性、大额加队长审钱，通过后采购/领用执行，物资台账自动增减。

**字段与校验**（详见 §6.1 硬件申请表）：物料名称/规格型号/数量/用途/期望日期必填；**新购必填购买链接**；数量 > 0；加急需填原因。

**审批路由**（按 flows:config 阈值，默认）：
- 库存领用 → 对应组组长单级。
- 新购 < 200 元 → 组长单级。
- 新购 ≥ 200 元 → 组长→队长顺序审批。
- 新购 ≥ 1000 元 → 再加指导老师会签。

**流程特有规则**：
- **台账联动**：状态"已领用" → 物资台账同名物料数量 −申请数量（物料名模糊匹配，匹配不到则创建新物料行并标"待补录位置"）；状态"已到货"（新购）→ 台账 +数量。联动写入走 MCP 工具 `update_inventory`（本期新增，幂等：按申请单号去重）。
- 执行人动作：采购执行人（运营组或指定队员）点"确认到货" → 状态"已到货" + 触发入库通知 + 台账增加；领用执行人（仓库管理员）点"确认出库" → 状态"已领用" + 台账扣减。
- 已通过但 14 天未执行 → 自动置"已取消"并通知申请人（防僵尸单）。

**验收**：
1. 新购 199 / 200 / 1000 元三档路由正确。
2. 领用单通过后台账数量正确 −1；新购到货后台账 +N。
3. 台账联动重复触发不产生重复增减（幂等）。

### F-03 合规审批【P1】

**用户故事**：作为宣传组，我发布海报/推送/视频前提交合规审批，通过后发布并回填链接存档，对外内容全程可追溯。

**字段与校验**（详见 §6.1 合规申请表）：合规类型/标题/内容说明/待审物料/涉及平台/计划发布时间必填；**赞助商相关 = 是时需填赞助商要求**；合规类型为"规则自查"时待审物料可为文字说明。

**审批路由**：宣传发布/肖像授权 → 运营组组长单级；**含赞助商相关或对外合作 → 加指导老师顺序会签**；比赛规则自查 → 组长单级。

**流程特有规则**：
- 时限规则：计划发布时间 T-2 前提交（应用页选早于 T-2 的日期时提示但不强制拦截）；T-1 仍审批中 → 待办条对审批人标红（见 A-01）。
- 驳回原因标准化选项：队标使用不规范 / 赞助商 logo 或露出错误 / 敏感信息 / 比赛规则风险 / 其他（必填说明）。
- 通过后：申请人执行发布 → 回填发布链接 → 点"已发布" → 状态"已发布"；季度末由运营组批量"已存档"。
- 对外合作类型通过后，合作文件（合同/协议扫描件）强制存飞书云盘并在底表"归档链接"字段登记。

**验收**：
1. 含赞助商的宣传单走两级；规则自查走单级。
2. 通过后回填链接 → "已发布" → 底表可查链接。
3. 驳回原因选项化并可统计（各原因驳回次数出现在校验报告）。

### 6.2 审批状态机

共享基座（引擎驱动）：`提交 → 审批中 →（飞书审批事件/轮询）→ 已通过 / 已驳回 / 已撤销`
各流程的**人工后续状态**由对应应用页动作按钮驱动：

```
reimburse   已通过 → 已打款（财务） → 已完成
drawing     已通过 → 加工中（申请人） → 已归档；驳回 → 改版本重提（新行）
hardware    已通过 →（新购）采购中 → 已到货 →（自动台账+）；→（领用）已领用（台账−）
compliance  已通过 → 已发布（回填链接） → 已存档
```

- 状态唯一自动变更入口：A-02 双通道回写 + 各页明确的动作按钮 API。任何人工直接改表的状态，数据校验 Agent（FE-05）扫出"无审批实例的状态变更"异常。
- "已取消"（hardware 14 天未执行自动取消）由 Cron 驱动，同样留痕。

## 7. API 契约（REST）

统一约定：除标注公开的接口外，均需 session Cookie；匿名 → 401 `{error:"unauthorized"}`；角色不足 → 403 `{error:"forbidden", role:"..."}`。

### POST /api/approvals — 发起审批（四流程统一入口）
请求：`{type: "reimburse"|"drawing"|"hardware"|"compliance", fields: {...}}`
fields 按 §6.1 对应表的必填/条件必填校验（引擎读 flows:config 的声明式规则）。
响应 200：`{application_id, instance_code, status:"审批中"}`
错误：400（含缺项列表）/ 401 / 403（越组提交）。

### GET /api/todos — 我的待办
响应：`{by_type: { reimburse: [...], drawing: [...], ... }, overdue_tasks: [...], cached_at}`，每项含 `url` 跳飞书审批详情。

### POST /api/approvals/events — 飞书审批事件回调（仅飞书调用）
验签 + URL 校验挑战；事件解密后经 `approval:map` 定位底表行更新状态；未知实例 code 记录告警但不抛错。

### 各流程动作按钮（统一前缀 `/api/approvals/<type>/<id>/...`）
| 端点 | 限角色 | 语义 |
|---|---|---|
| `.../reimburse/:id/pay` | 财务/队长 | 标记已打款（幂等） |
| `.../drawing/:id/start` `:id/archive` | 申请人 | 开始加工 / 归档 |
| `.../hardware/:id/arrive` | 执行人（组长指定） | 确认到货 → 台账 + |
| `.../hardware/:id/issue` | 仓库管理员 | 确认出库 → 台账 − |
| `.../compliance/:id/publish` | 申请人 | 回填链接 → 已发布 |

**权限备注**：飞书审批待办 API 需要 user_access_token。当前 session 只存 user_info，不存 user_access_token（2 小时过期）。方案：登录时把 user_access_token 与 refresh_token 存入 KV `oauth:<open_id>`（refresh_token 14 天有效），待办接口用 refresh 流程换新。refresh_token 持久化需在 FE-01 登录流程上小改——**这是本 PRD 对 FE-01 的唯一反向依赖，已在 §9 排期 M1.5 体现**。

## 11. 风险与边界

- **飞书审批 API 免费版限制**（最高风险）：§9 的 1 小时验证不过 → Plan B 引擎（状态机落表 + 群机器人通知），接口契约不变。
- **事件回调丢消息**：双通道回写（事件主、轮询兜）已内建；轮询 5 分钟，时延目标仍满足。
- **user_access_token 过期**：M1.5 的 refresh_token 方案；refresh 失败时待办条降级提示"重新登录"。
- **台账联动错配**：物料名模糊匹配可能匹配错行 → 联动必须经 `update_inventory`（幂等 + 留痕 ref_id），人工可回滚；匹配置信度低时（多名相似物料）只通知不自动改。
- **图纸版本覆盖**：D 维度强制"重提 = 新行"，应用层禁止同 record_id 覆盖附件；校验 Agent 加规则"同图号版本号必须递增"。
- **审批人缺位**：见 §3 代理人规则；M2 落地时必须至少配好各流程默认代理人，否则审批卡死。
- **范围纪律**：请假等更多流程走"零代码新增"通道（§6.1 配置式扩展）；对外合作合同流转（盖章/签字链）不在本期，归合规审批的"对外合作"类型兜底。
- **数据归属**：审批实例存飞书；中台 KV 只存映射与缓存，赛季结束归档方式同 V2.0 数据层约定。
