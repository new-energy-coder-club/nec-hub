# PRD：协议签署 OA 审批流程

| 项目 | 内容 |
|---|---|
| 文档版本 | V1.0 |
| 创建日期 | 2026-10-14 |
| 状态 | 已评审通过（2026-10-15，带修订建议），附录 A 待评审会拍板 |
| 适用平台 | 飞书审批（OA） |
| 需求来源 | 合作协议与保密协议签署需法务、运营、合规三级审核 |

---

## 1. 背景与问题

当前合作协议与保密协议（NDA）的签署缺乏统一的线上审批通道，存在以下问题：

- 协议签署前未经法务、运营、合规的系统性审核，存在法律与合规风险
- 审核过程依赖线下沟通与即时消息，无留痕、不可追溯
- 协议版本、签署状态分散管理，无法统一查询

## 2. 目标

- 在飞书审批平台上线「协议签署审批」定义，覆盖**合作协议**与**保密协议**两类协议
- 固化 **法务 → 运营 → 合规** 三级串行审核流程，全部通过后方可签署用章
- 全流程线上留痕，审批记录可查询、可追溯

### 2.1 成功指标

| 指标 | 目标值 |
|---|---|
| 协议签署线上审批覆盖率 | 100% |
| 单流程平均审批时长 | ≤ 3 个工作日 |
| 审批驳回原因可追溯率 | 100% |

## 3. 范围

### 3.1 本期包含（In Scope）

- 「协议签署审批」审批定义的表单设计与流程配置
- 法务、运营、合规三级串行审批节点
- 审批通过与驳回的消息通知
- 协议附件上传与归档留存

### 3.2 本期不包含（Out of Scope）

- 电子签章系统集成（后续迭代）
- 与合同管理系统（CLM）的数据打通（后续迭代）
- 除合作协议、保密协议外的其他协议类型（预留扩展）

## 4. 角色定义

| 角色 | 职责 |
|---|---|
| 发起人 | 填写协议信息、上传协议文本附件、跟进审批进度 |
| 法务审核人 | 审核协议条款的合法性、权利义务、违约责任等 |
| 运营审核人 | 审核合作模式、商务条款、资源投入与业务匹配度 |
| 合规审核人 | 审核数据合规、资质合规、监管要求符合性，终审把关 |
| 审批管理员 | 维护审批定义、节点人员与权限配置 |

## 5. 功能需求

### 5.1 审批定义基本信息

| 配置项 | 值 |
|---|---|
| 审批名称 | 协议签署审批 |
| 审批分组 | 法务合规 |
| 可见范围 | 全体成员（或按部门限定） |
| 审批说明 | 合作协议、保密协议签署前的法务/运营/合规联合审核 |

### 5.2 表单字段设计

| 序号 | 控件名称 | 控件类型 | 必填 | 说明 |
|---|---|---|---|---|
| 1 | 协议类型 | 单选 | 是 | 选项：合作协议 / 保密协议（NDA） |
| 2 | 合作方名称 | 单行文本 | 是 | 对方公司/机构全称 |
| 3 | 合作方统一社会信用代码 | 单行文本 | 否 | 便于法务与合规核验主体资质 |
| 4 | 协议主题 | 单行文本 | 是 | 一句话概括合作/保密事项 |
| 5 | 协议期限 | 日期区间 | 是 | 协议生效日至到期日 |
| 6 | 涉及金额 | 金额 | 否 | 无金额协议（如纯 NDA）可留空 |
| 7 | 我方签署主体 | 单行文本 | 是 | 我方签约公司主体全称 |
| 8 | 协议文本附件 | 附件 | 是 | 上传待审核的协议 Word/PDF |
| 9 | 补充材料 | 附件 | 否 | 资质证明、背景资料等 |
| 10 | 事项说明 | 多行文本 | 是 | 合作背景、紧急程度、特殊条款说明 |
| 11 | 期望签署日期 | 日期 | 否 | 供审核人评估优先级 |

### 5.3 审批流程设计

```text
发起人提交
   │
   ▼
① 法务审核 ──驳回──▶ 退回发起人（修改后可重新提交）
   │ 通过
   ▼
② 运营审核 ──驳回──▶ 退回发起人
   │ 通过
   ▼
③ 合规审核（终审）──驳回──▶ 退回发起人
   │ 通过
   ▼
审批通过 → 抄送发起人 + 印章管理员，进入签署用章环节
```

节点配置明细：

| 节点 | 审批人类型 | 审批方式 | 驳回策略 |
|---|---|---|---|
| ① 法务审核 | 指定成员/角色（法务） | 或签（任一通过即可） | 驳回到发起人 |
| ② 运营审核 | 指定成员/角色（运营负责人） | 或签 | 驳回到发起人 |
| ③ 合规审核 | 指定成员/角色（合规负责人） | 或签 | 驳回到发起人 |
| 抄送节点 | 发起人、印章管理员 | — | 审批通过后触发 |

> 若审核职责由多人分担，节点审批方式建议「或签」；如需多人全部确认，改为「会签」。

### 5.4 通知与提醒

| 触发时机 | 通知对象 | 渠道 |
|---|---|---|
| 待办产生 | 当前节点审批人 | 飞书审批待办 + 应用消息 |
| 超过 24h 未处理 | 当前节点审批人 | 自动催办提醒 |
| 审批通过 | 发起人、印章管理员 | 应用消息 |
| 审批驳回 | 发起人 | 应用消息（含驳回意见） |

### 5.5 权限要求

- 表单数据：仅发起人、各节点审批人、抄送人、审批管理员可见
- 协议附件：随表单权限，不对外公开
- 审批记录：审批管理员可导出用于审计

## 6. 异常与边界场景

| 场景 | 处理策略 |
|---|---|
| 审批人离职/转岗 | 管理员在后台更新节点审批人；在途单据转交继任者 |
| 紧急协议 | 发起人在「事项说明」中标注紧急，审批人加急处理；支持人工催办 |
| 协议文本审批后变更 | 需撤回原实例，重新发起审批 |
| 同一合作方多份协议 | 每份协议单独发起一个审批实例，互不合并 |

## 7. 落地步骤

1. 管理员在 **飞书管理后台 → 审批** 新建「协议签署审批」定义（按 5.2 表单、5.3 流程配置）
2. 配置节点审批人（法务/运营/合规对应成员或角色）与抄送人
3. 小范围灰度：选 1-2 个真实协议走完整流程验证
4. 全员公告上线，旧线下流程废止
5. 上线后可通过 API（`approval_code`）支持机器人代发起提单

## 8. 后续迭代方向

- 接入电子签章，审批通过后自动流转签署
- 协议到期前自动提醒（结合协议期限字段）
- 与合同管理台账多维表格联动，审批通过自动归档
- 扩展协议类型：采购合同、服务合同、战略合作协议等

## 附录 B. 后台配置清单（评审通过后管理员执行）

1. **新建审批定义**：飞书管理后台 → 审批 → 审批管理 → 新建审批
   - 名称「协议签署审批」、分组「法务合规」、可见范围按 A3 结论、说明按 §5.1
2. **配置表单**：按 §5.2 表逐一添加 11 个控件，注意必填项与控件类型（日期区间、金额、附件、单选选项值）
3. **配置流程**：按 §5.3 依次添加 法务 → 运营 → 合规 三个审批节点
   - 每个节点：审批人按 A1 结论，审批方式按 A2 结论，驳回策略「驳回到发起人」
   - 通过后抄送节点：发起人 + 印章管理员
4. **配置通知**：开启待办与应用消息；按 A4 结论设置 24h 自动催办
5. **权限核对**：表单与附件可见性按 §5.5（发起人/审批人/抄送人/管理员）
6. **记录 `approval_code`**：定义发布后取得，存档备查（后续 API 代提单使用）
7. **灰度验证**：按 A5 选定的真实协议走完整流程（提交 → 三级审批 → 抄送 → 归档），验证通过后全员公告上线

修订建议（不阻塞立项，随 V1.1 修订吸收）：

1. **补充「与既有实现的关系」一节**：仓库已存在 `src/cla/` 模块与 `public/apps/contract-signing/` 子应用，且《协议签署OA_飞书后台配置手册》已就本 PRD 的后台配置给出操作步骤。应明确：本 PRD 范围 = 飞书原生审批定义侧；中台子应用 = 门户入口与台账联动侧，二者关系与边界需写清，避免后续双实现漂移（参照结构优化 PRD 的 ST-03 教训）。
2. **§2.1 成功指标补度量口径**：「线上审批覆盖率 100%」「≤3 个工作日」需写明数据来源（飞书审批后台导出？台账表统计？）与统计周期，否则验收时无法取证。
3. **§3.1「归档留存」需指明归档位置**：建议本期即明确最小版——附件随审批实例留存 + 审批通过后在合同台账多维表格登记一行（即 §8 迭代方向第 3 条的最小实现），否则「可追溯」指标落空。
4. **角色现实性**：学生战队一般无法务/合规专职岗，A1 的选项应允许「指导老师/队长兼任」并注明兼任时的利益冲突规避（发起人与终审不得同人）。
