## 1. 背景与问题

对标文章的"邮件OA审批"由三个互相独立的部件组成，缺一不可：

| 对标部件 | 说明 | 我方现状 |
|---|---|---|
| 审批中心 | 中台侧栏"审批"入口，聚合待办（角标数量） | 代码 0；V2.0 FE-09（P2）仅一句"聚合飞书审批待办" |
| 标杆审批应用（发票助手） | 提交开票申请 → 飞书机器人通知财务 → 核对一键处理 → 状态回写 | 代码 0；V2.0 FE-08（P1）仅有用户故事 |
| 邮件通道 | 生成确认邮件草稿、自动抄送 COO | 代码 0；Worker 无法直发 SMTP，通道未选型 |

**为什么要现在写详细 PRD**：FE-01 登录态已落地（工作区），审批链路的公共前置只剩 FE-02（4 张底表落地）。V2.0 的 FE-08/FE-09 粒度只到"用户故事 + 3 条验收"，无法直接开发——缺审批引擎选型、状态机、字段级表结构、接口契约、通知通道选型。本 PRD 补齐这些。

**范围纪律**：本期只做"报销审批"一条业务线 + 通知通道 + 待办聚合。物资领用、请假等第二条业务线复用同一引擎与通道，但不进本期排期（见 §9 里程碑 M2.5）。

## 2. 目标与成功指标

**产品目标**：队员提交报销 → 审批人飞书收到通知 → 审批通过自动回写财务底表 → 全队按角色看到正确的待办与汇总，全程零人工传话。

| 指标 | 定义 | 目标值 | 测量方式 |
|---|---|---|---|
| 报销线上化率 | 走报销助手的单数 / 全队报销总单数 | 上线 4 周后 ≥ 80% | 财务报销表"来源"字段统计 |
| 审批时延 | 提交 → 审批人收到飞书通知 | P95 ≤ 2 分钟 | 审批实例时间戳差 |
| 状态回写准确率 | 审批结果与财务表状态一致的单数占比 | ≥ 98%，不一致需人工可解释 | 对账抽查 |
| 通知到达率 | 通知发送成功 / 应发通知 | ≥ 95%（失败自动降级通道） | 通知发送日志 |
| 待办准确性 | 待办条显示数与飞书审批中心实际待办数一致 | 100%（≤5 分钟缓存窗口） | 验收测试用例 |

## 4. 总体设计

### 4.1 三个子系统

```
┌──────────────────────────────────────────────────────────┐
│ 门户层                                                    │
│  · 报销助手页（/apps/reimburse/，经 deploy_app 上架）        │
│  · 待办条（首页顶部，所有 Tab 可见）                          │
├──────────────────────────────────────────────────────────┤
│ 中台 Worker 新增模块                                       │
│  · /api/approvals        审批封装（发起/列表/详情/回写状态）    │
│  · /api/todos            待办聚合（飞书审批 + 逾期任务）       │
│  · notify 模块           通知服务（飞书机器人 webhook 主通道）  │
│  · mailer 模块           邮件通道（Resend HTTP API，降级通道）  │
│  · MCP 新增工具：submit_approval / list_todos / send_notice  │
├──────────────────────────────────────────────────────────┤
│ 飞书侧                                                    │
│  · 飞书审批（引擎）：报销审批定义 + 审批实例 + 待办            │
│  · 群机器人 webhook（通知主通道）                             │
│  · 多维表格：财务报销表（底表，状态回写目的地）                  │
└──────────────────────────────────────────────────────────┘
```

### 4.2 关键决策

**D1 审批引擎用飞书审批，不自建状态机。**
理由：① 通知原生（审批机器人自动推送给审批人，免做触达）；② 权限复用飞书（FE-01 原则）；③ 待办可直接拉飞书审批 API，不用自维护待办表；④ 免费版可用（需管理员在飞书审批后台确认自建应用可发起审批，**排期前先用 1 个测试审批验证，验证不过则启动 Plan B**）。
Plan B（降级）：状态机落在"财务报销表.状态"字段（见 §6.2），通知走群机器人 webhook，待办条改为查表。语义与接口契约不变，仅引擎实现替换。

**D2 通知主通道 = 飞书群机器人 webhook，邮件 = 降级/可选增强。**
对标文章的"生成邮件草稿抄送 COO"在我们环境落不了地（无 Gmail/企业邮箱 API，Worker 不能 SMTP）。替换为：审批动作实时推飞书群（含审批卡片链接），邮件仅在配置了 `RESEND_API_KEY` 时启用。学生团队场景飞书打开率远高于邮箱，这是对标杆的合理本地化。

**D3 数据不下沉**：审批单明细存飞书（审批实例 + 财务报销表），中台只存映射与短期缓存（KV），退队即失效。

## 5. 功能需求

优先级：P0 阻塞链路，P1 完整闭环，P2 增强。

### N-01 通知服务（飞书群机器人 webhook）【P0】

**用户故事**：作为系统，任何审批事件都能在 2 分钟内推送到指定飞书群，且失败可感知。

**详细需求**：
- 封装 `notify(env, { title, content, link? })`：POST 到群机器人 webhook（secret 存 `FEISHU_BOT_WEBHOOK` secret，支持加签校验）。
- 签名实现：若 webhook 含 secret，按飞书加签算法（timestamp + "\n" + secret 的 HMAC-SHA256 → Base64）发送。
- 重试：失败（网络错误/非 0 code）重试 2 次，指数退避（1s/4s）；仍失败写入 KV `notify:failed`（保留 7 天），管理端可查。
- 消息格式：`post` 富文本，标题 + 关键字段表 + "去处理"链接（跳审批详情）。
- 群分流：默认一个"NEC 中台通知"群；财务类通知额外支持第二个 webhook（`FEISHU_BOT_WEBHOOK_FINANCE`），未配置则 fallback 主群。

**验收**：
1. 触发测试事件，群 10 秒内收到格式正确的消息。
2. 故意填错 webhook，重试 2 次后 `notify:failed` 出现一条记录，接口返回降级提示。

### N-02 邮件通道（Resend）【P2】

**详细需求**：
- 仅当配置 `RESEND_API_KEY` 与 `MAIL_FROM` 时启用；未配置时所有邮件调用返回"通道未启用"，业务不受影响。
- 经 Resend HTTP API 发送（Worker 内 fetch，无 SMTP）。
- 模板：纯 HTML 内联样式一封（报销确认通知），字段：申请人/金额/事项/审批链接。
- 免费额度约 100 封/天（以官网为准），只发"审批结果"与"周报摘要"两类低频邮件，其余全走飞书。

**验收**：配置后触发审批通过事件，收件箱收到渲染正确的邮件；未配置时接口明确返回 disabled 而非报错。

### A-01 待办条（V2.0 FE-09 详细化）【P1】

**用户故事**：作为队长/财务，打开中台首页就看到"待我审批的报销 N 条、逾期任务 M 条"，点开即处理。

**详细需求**：
- 位置：门户 Hero 下方横条，未登录不渲染。
- 数据源与缓存：
  - 飞书审批待办：`GET /open-apis/approval/v4/todo`（需 user_access_token——前端场景用当前登录 session 换；见 §7 权限备注），KV `todo:<open_id>` 缓存 5 分钟。
  - 逾期任务：查任务进度表（复用现有 `fetchTableCached`），截止 < 今天 且状态未完成，按负责人过滤当前用户，缓存 5 分钟。
- 展示：`<待办图标> 待审批报销 2 · 逾期任务 1`，点击展开下拉（标题 + 截止时间 + 跳转链接），跳转飞书审批详情/多维表格行。
- 角标数字与下拉列表必须一致（同源数据）。

**验收**：
1. 造 1 条待审批 + 1 条逾期任务，登录后 10 秒内条上出现，数字正确。
2. 点审批项跳飞书处理完返回，≤5 分钟后数字减少（缓存窗口内允许延迟，文档注明）。
3. 无待办时整条隐藏。

### A-02 审批发起与状态回写【P0】

**用户故事**：作为队员，我在报销助手提交后，系统自动发起飞书审批；作为财务，我在飞书点通过后，中台财务表状态自动变为"已通过"，无需任何人手改表。

**详细需求**：
- 发起：队员在报销助手确认提交 → Worker `POST /api/approvals` → 调飞书审批 `POST /approval/v4/instances`（approval_code=`报销审批定义`，form 含金额/事项/发票附件链接）→ 返回实例 code → 写入财务报销表新行（状态="审批中"，实例 code 存"审批实例"字段）。
- 回写（双通道，都做）：
  1. 事件回调：飞书审批状态变更推送到 Worker `POST /api/approvals/events`（配置 encrypt key / verification token），解密验签后更新财务表状态字段。
  2. 轮询兜底：Cron Trigger 每 5 分钟扫财务表中"审批中"且 30 分钟未更新的行，逐条 `GET /approval/v4/instances/:code` 同步状态。事件通道为主，轮询兜漏。
- 状态映射：`审批中 /approved→已通过 /rejected→已驳回 /canceled→已撤销`；通过且财务确认打款后，财务可在报销助手点"已打款"置"已完成"。
- 通知钩子：发起成功 → 群通知"新报销申请"；通过/驳回 → 通知申请人 + 财务群。

**验收**：
1. 端到端走通一单测试报销：提交 → 财务飞书收到审批 → 通过 → ≤5 分钟内财务表状态变"已通过"（两个回写通道各自断一个都能收敛）。
2. 驳回路径同样验证。
3. 队员账号调 `POST /api/approvals` 成功，校友账号调返回 401。

### R-01 报销助手（标杆应用，V2.0 FE-08 详细化）【P1】

**用户故事**：作为队员，我拍一张发票传上去，填金额和事项，系统告诉我材料齐不齐，确认提交后等审批结果就行。

**详细需求**（按页面步骤）：
1. **上传/录入**：发票照片传 R2（`reimburse/<open_id>/<uuid>.jpg`，7 天生命周期）→ OCR（优先飞书 OCR API，失败降级手动录入金额/日期/发票号）。展示识别结果供确认修改。
2. **SOP 校验**：按"财务报销 SOP"（资料页 FE-03 的同一份）做规则校验：金额 > 0；事项非空；发票号 8 位或 20 位；日期在本赛季内；有发票照片或"无票说明"。不通过则列出缺项，不允许提交。
3. **确认提交**：展示汇总卡（金额/事项/发票/抄送人）→ 确认 → `POST /api/approvals`（见 A-02）→ 成功页显示"审批中 + 实例链接"。
4. **我的报销**：当前用户的历史申请列表（查财务表按申请人过滤），状态徽章可视化。
5. 通过 `deploy_app` 上架，作者署名，visibility 全队可见（财务字段仍按 A-01 权限脱敏——应用内明细仅本人+队长/财务可见）。

**验收**（沿用并细化 V2.0 FE-08）：
1. 完整链路走通一单真实报销；财务表记录字段齐全无空值。
2. 材料不全时提交按钮不可用，缺项提示准确。
3. 非作者队员打开"我的报销"看不到他人明细。
4. 复盘文档进资料页"标杆案例"。

### 6.2 审批状态机

```
            提交                发起成功               飞书审批事件/轮询
 [草稿] ────────▶ [审批中] ─────────────────────▶ [已通过] ──财务确认──▶ [已打款] ──▶ [已完成]
                                      │                    （驳回后可重新编辑提交，
                                      ▼                     生成新单号，旧单保留）
                                 [已驳回] / [已撤销]
```

- 状态唯一变更入口：A-02 回写通道（事件 + 轮询）。任何人工直接改表的状态，下次校验 Agent（FE-05）扫出"无审批实例的状态变更"异常。
- "已打款/已完成"不由飞书审批驱动，由财务在报销助手点击（`POST /api/approvals/:id/pay`，仅财务角色）。

### 6.3 KV 键设计

| 键 | 内容 | TTL |
|---|---|---|
| `todo:<open_id>` | 待办聚合结果 | 300s |
| `approval:map:<实例code>` | 实例 → 财务表 record_id | 90 天 |
| `notify:failed` | 发送失败记录（list，截断 100 条） | 7 天 |
| `role:<open_id>` | 角色缓存（现有） | 60s |

## 7. API 契约（REST）

统一约定：除标注公开的接口外，均需 session Cookie；匿名 → 401 `{error:"unauthorized"}`；角色不足 → 403 `{error:"forbidden", role:"..."}`。

### POST /api/approvals — 发起报销审批
请求：`{amount:number, item:string, invoice_no?:string, invoice_urls?:string[], no_invoice_reason?:string}`
响应 200：`{application_id:"BX-2026-0001", instance_code:"...", status:"审批中"}`
错误：400 参数校验失败（含 SOP 缺项列表）；401/403 见约定。

### GET /api/todos — 我的待办
响应：`{approvals:[{code,title,submitted_at,url}], overdue_tasks:[{record_id,title,deadline,url}], cached_at}`

### POST /api/approvals/events — 飞书审批事件回调（仅飞书调用）
飞书侧配置 encrypt key + verification token；首验 URL 校验挑战；事件解密后更新财务表。

### POST /api/approvals/:id/pay — 标记已打款（仅财务/队长）
响应：`{status:"已打款"}`；幂等（重复调用返回当前状态）。

**权限备注**：飞书审批待办 API 需要 user_access_token。当前 session 只存了 user_info，不存 user_access_token（2 小时过期）。方案：登录时把 user_access_token 与 refresh_token 存入 KV `oauth:<open_id>`（refresh_token 14 天有效），待办接口用 refresh 流程换新。refresh_token 的持久化需在 FE-01 登录流程上小改——**这是本 PRD 对 FE-01 的唯一反向依赖，已在 §9 排期 M1.5 体现**。

## 11. 风险与边界

- **飞书审批 API 免费版限制**（最高风险）：§9 的 1 小时验证不过 → Plan B 引擎（状态机落表 + 群机器人通知），接口契约不变。
- **事件回调丢消息**：双通道回写（事件主、轮询兜）已内建；轮询扫表频率 5 分钟，时延目标仍满足。
- **user_access_token 过期**：M1.5 的 refresh_token 方案；refresh 也失败时待办条降级显示"重新登录后可见审批待办"。
- **OCR 准确率**：首期允许手动录入兜底（V2.0 已定），发票识别放二期，不阻塞闭环。
- **范围纪律**：物资领用/请假审批 = 第二个审批定义 + 复用全部通道，排期另议，不进本期。
- **数据归属**：审批实例存飞书；中台 KV 只存映射与缓存，赛季结束归档方式同 V2.0 数据层约定。
