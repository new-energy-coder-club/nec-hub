## 1. 背景与目标

### 1.1 背景

- 战队报销长期靠群里发发票照片 + 队长的表格手工登记，状态不透明、易漏单、无留痕。
- V2.0 将报销助手定为 FE-08（P1，M2 里程碑），同时承担**标杆应用**职责：作为队员 Vibe Coding 的复刻样板（V2.0 §14.1 上手路径第 2 步直接引用本应用复盘）。
- 截至 2026-10-15，功能代码已全部上线，只差端到端真实验收与收尾决策。

### 1.2 目标

**产品目标**：队员拍发票 → 自动识别 → 材料自检 → 提交 → 等结果，全程零人工传话；审批结果自动回写财务底表；本人随时可查历史单据与状态。

**标杆目标**：全链路（静态页 + Worker API + D1 + R2 + 审批引擎 + 飞书回写）代码可読、可复刻，复盘文档进资料页「标杆案例」。

## 2. 目标与成功指标

| 指标 | 定义 | 目标值 | 测量方式 |
|---|---|---|---|
| 端到端时长 | 队员从打开应用到提交成功的耗时 | ≤ 3 分钟（有票） | 实测计时，验收 §13-1 |
| 一次通过率 | 提交后不因材料缺项被驳回的单据占比 | ≥ 90% | 上线后 1 个月统计审批记录 |
| OCR 回填准确率 | 金额/日期/发票号三字段抽查准确占比 | ≥ 80%（不准则可手改，不阻塞） | 抽 20 张真实发票人工核对 |
| 状态回写时延 | 审批动作 → 财务底表状态正确 | ≤ 5 分钟 | 验收 §13-1 实测 |
| 权限隔离 | 非本人/非队长/财务无法查看他人单据明细 | 100%（403） | 测试用例 + 走查 |
| 标杆复用 | 复盘文档发布后，至少 1 名队员参照复刻出一个新应用 | 1 个 | 应用广场上架记录 |

## 3. 详细需求（按页面步骤）

### 3.1 登录与门禁

- 飞书 OAuth 登录（复用 FE-01 `/auth/feishu` + `whoami`）；未登录显示登录门禁页。
- `role === "external"`（校友/外部）提交返回 403（`src/erp/reimburse.ts:176`）；全队正式成员均可提交（flows 配置 `group: null` 不限组别）。

### 3.2 基本信息与报销明细

- 单据号提交后自动生成（`BX-<年份>-<序号>`，由审批引擎 `src/approvals/engine.ts:103` 统一发号）；单据日期只读为当天。
- 明细为行式表格（增/删行，≤50 行），列：费用项目（弹窗树选择，目录来自 D1 `expense_items`，4 大类 17 项 + F99.01 其他）/ 事项说明 / 开票日期 / 发票号 / 金额。
- 「选中行」语义：费用项目选择与附件 OCR 回填均作用于当前选中行。
- 草稿自动保存 localStorage（`nec_reimburse_erp_draft`），支持「暂存」，提交前可继续编辑。

### 3.3 OCR 识别（本地，零成本）

- 技术栈：Tesseract.js v5（CDN 双源 fallback）+ pdfjs-dist（PDF 渲染前 3 页 scale=2 后识别），语言 `chi_sim+eng`。**不调飞书 OCR API、不引入付费 API**（与 V2.0 §10 OCR 成本风险项一致）。
- 字段抽取：金额按「(小写) → 价税合计 → 合计/总计/实付/金额/付款/支付 → ¥￥」四级正则依次匹配；开票日期 `20xx[-/年.]mm[-/月.]dd`；发票号 `发票号码\D{0,4}(\d{20}|\d{8})` 或裸 20 位。
- 回填策略：**只回填选中行的空字段，不覆盖人工修改**；发票号仅从「发票」槽位回填；识别结果展示供确认。
- 识别失败降级为纯手动录入，不阻塞提交。

### 3.4 收款信息

- 收款方式（select）/ 户名（默认本人）/ 账号 / 开户行（电汇必填）。
- 「存为我的默认收款账户」勾选后 `PUT /api/erp/reimburse/payee` 异步入库（D1 `payees`，open_id 一人一条 upsert），下次打开自动带出。

### 3.5 附件与 SOP 校验

- 附件槽位：发票 + 付款凭证，各 ≤10 个、单文件 ≤10MB，支持选择文件与 Ctrl+V 粘贴；先传 R2（`/api/approvals/upload` → `receipts/<yyyymmdd>/`），提交时以 key 引用。
- SOP 校验 5 项（前后端同源，未通过逐项列缺、提交按钮不可用）：
  1. 至少一行明细，且每行费用项目/事项/金额齐全（金额 > 0，至多两位小数，`/^\d{1,7}(\.\d{1,2})?$/`）；
  2. 发票号为 8 或 20 位数字（`INVNO_RE`）；未填整单无票说明时至少一行须填发票号；
  3. 开票日期在本赛季（当年 1-1 起）且不晚于今天；
  4. 有发票附件**或**填写整单无票说明（对应 flows 配置 `conditional` 规则）；
  5. 无进行中的 OCR 任务。

### 3.6 提交与状态回写

- 确认提交 → `POST /api/erp/reimburse/submit`：
  - 服务端复检 SOP（`validateErpDoc`）→ 整单快照写 D1 `reimburse_docs`（payload_json 全量）→ 经审批引擎创建 BX 单 → 字段映射写飞书「财务报销」底表（事项=明细全文 / 报销金额=合计 / 发票号=去重合并 / 无票说明 / 来源=报销助手 / 发票照片=R2 keys）→ 通知审批人（标题「📋 新报销申请 BX-2026-0001（张三 ¥120）」）。
- 成功页显示申请单号 + 「再报一笔」；审批动作（approve/reject/pay）由引擎统一处理，状态以飞书底表为准，回写时延 ≤5 分钟（继承 V1.1 §15 DoD）。
- **旧接口退役决策（本期 P0）**：`POST /api/reimburse`（`src/reimburse.ts`，直写看板表、不进审批流）与新链路双轨并存。决策：**冻结保留 30 天观察期（路由不删、文档标注废弃），本 PRD 验收通过后在下个迭代删除路由与 `src/reimburse.ts`**；`scripts/simulate-reimbursements.*`、根目录 4 份 REIMBURSE*.md 同步归档到 `docs/legacy/` 并注明仅适用旧接口。

### 3.7 与 V1.1 R-01 原始设计的差异对照（已落地为准）

| 项 | V1.1 R-01 原设计 | 实际落地 | 处置 |
|---|---|---|---|
| OCR | 优先飞书 OCR API，失败降级手动 | Tesseract.js 纯浏览器本地识别 | 接受落地（零成本、无隐私出域），V2.0 变更记录已记载 |
| R2 路径 | `reimburse/<open_id>/<uuid>.jpg` | `receipts/<yyyymmdd>/<uuid>-<文件名>` | 接受落地，按日期前缀便于生命周期管理 |
| R2 生命周期 | 7 天自动删除 | 未配置生命周期规则 | 见 §9 风险 R-2，本期决策：凭证属财务存档，**不配置自动删除** |
| 接口形态 | `POST /api/approvals` type=reimburse | `/api/erp/reimburse/submit` 封装引擎调用 + D1 快照 | 接受落地（ERP 体验需要整单快照） |

### 3.8 我的报销

- 当前用户历史单据列表（D1 快照 + 审批状态合并，提交时间降序，前 20 条），状态徽章（暂存=灰/审批中=蓝/已通过/已驳回/已打款）。
- 支持「查看」（只读详情）与「复制」（以该单为模板新增）。
- 权限：明细仅本人 + 队长/财务可见（服务端校验，403 而非前端隐藏）。

### 3.9 上架与可见性

- 通过 `deploy_app` 上架应用广场（`/apps/reimburse/`），作者署名，visibility=all；明细数据按 §3.8 服务端隔离。

## 5. 数据模型（D1 `nec-hub-erp`，迁移 `migrations/erp/0001_reimburse_erp.sql`）

- **expense_items**：`code TEXT PK`（如 F38.01）、`grp`、`name`、`enabled`；种子 17 项（研发 F38.01~06 / 生产加工 F39.01~03 / 物料采购 F40.01~03 / 运营办公 F41.01~04 / 其他 F99.01）。
- **payees**：`open_id TEXT PK`、`method`、`account_name`、`account_no`、`bank`、`updated_at`。
- **reimburse_docs**：`application_id TEXT PK`（= BX 单号）、`open_id`、`applicant`、`payload_json`（lines/note/noinv/payee/attachments/fields 全量）、`status DEFAULT '审批中'`、`created_at`；索引 `idx_reimburse_docs_owner(open_id, created_at DESC)`。
- 分工约定：附件实体在 R2 `receipts/`；审批状态以飞书底表为准；D1 只存 ERP 整单快照。

## 6. 审批流程配置（flows:config · reimburse）

```ts
{
  engine: "table",                 // Plan B 底表引擎（feishu 引擎为预留）
  prefix: "BX",                    // 单号 BX-2026-0001
  group: null,                     // 全队可提交
  approvers: { roles: "队长|财务" },
  sla: { escalateHours: 48, autoCancelDays: 14, escalateTo: "队长" },  // 与四流程统一时效治理（V1.2 G-03）
  required: ["事项", "报销金额", "发票号"],
  conditional: [{ when: { field: "发票照片", equals: "" }, require: ["无票说明"] }],
}
```

底表配置（`tableId`/`base`）由 MCP `config_flows` 写入 KV，零代码可改。

## 7. 非功能性需求

- **成本**：OCR 纯前端零调用成本；D1/R2/KV 在 Cloudflare 免费额度内。
- **性能**：提交端到端（不含人工确认）< 2s（沿用旧接口测试基线）；OCR 识别单张 ≤ 15s（前端体验目标，超时可手动跳过）。
- **兼容**：飞书 WebView 可用（参照 FE-14 PRD §14.4 兼容口径）；CDN 双源 fallback 保障 Tesseract/pdfjs 加载。
- **安全**：附件 key 白名单正则 `/^receipts\/\d{8}\/[\w.\-一-龥]+$/`；明细 ≤50 行、附件 ≤10 个；财务数据按角色三级脱敏（继承 FE-01）。

## 9. 风险与依赖

| 编号 | 风险 | 影响 | 对策 |
|---|---|---|---|
| R-1 | 中文发票 OCR 准确率不达标 | 用户手改成本上升 | 定位为「辅助回填」而非准入条件；准确率 <60% 时降级为默认关闭、按钮手动触发 |
| R-2 | 凭证 R2 无生命周期规则，存储持续增长 | 长期成本 | 财务凭证属存档数据，本期明确**不自动删除**；每赛季末由财务导出备份后手工清理上一赛季 |
| R-3 | 旧接口双轨期间有人误用直写看板表 | 数据绕过审批 | 观察期内在旧接口响应与文档中标注 deprecated；门户/群通知统一入口为 `/apps/reimburse/` |
| R-4 | CDN（jsdelivr/tessdata）被墙导致 OCR 不可用 | 识别功能失效 | 已有双源 fallback；完全失败时降级手动录入，不阻塞提交 |
| R-5 | 依赖 FE-01 登录态、审批引擎、财务底表配置 | 上游故障即不可用 | 继承 V1.1/V1.2 的降级路径；flows:config 缺失时回退默认配置 |

## 10. 测试策略

- **单测**（已有，`src/__tests__/erp-reimburse.test.ts`）：validateErpDoc 校验、buildApprovalFields 映射、meta/payee upsert、submit 全链路、附件 key 白名单、docs 权限（本人/队长/财务）。新增代码必须保持该文件全绿。
- **端到端实测（本期 P0）**：
  1. 真实一单：队员账号拍真实发票 → OCR 回填 → 提交 → 审批人飞书收到通知 → 通过 → ≤5 分钟财务底表状态正确、字段齐全无空值；
  2. 驳回路径 1 次（驳回原因可见）；
  3. 材料不全组合（无票无说明 / 发票号位数错误 / 日期超赛季）提交按钮均不可用且缺项提示准确；
  4. 权限：队员 B 无法查看队员 A 的单据详情（403）；external 账号提交 403；
  5. OCR 抽查：20 张真实发票，金额/日期/发票号准确率分别记录。
- **回归**：mine 接口泛化后报销页回归已过（V1.2 G-02 交付记录，`vitest 242/242`）；后续引擎改动须复跑报销域用例。
